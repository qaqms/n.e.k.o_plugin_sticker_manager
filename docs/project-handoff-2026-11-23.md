# 表情包插件项目与当前进度交接

更新日期：2026-11-23

## 项目目标

`sticker_manager` 是 N.E.K.O 的表情包插件，提供可整理的图片收藏库，并在正常聊天中选图、发送图片。插件既有主模型工具模式，也有宿主回复完成钩子模式。

本轮要解决的产品目标是：**用户不必另外为表情包插件创建或绑定一个模型，插件便能使用宿主提供的模型完成选图。** 这里的“不用额外配置”指不必配置插件专属模型槽位；宿主本身仍须有一个可用的模型配置或可用的免费模型服务。

目标不是让模型无条件发图。插件仍应服从纯文字要求、语境和候选图片匹配；网络失败、无合适图片或图片提交失败时，应允许本轮不发。

## 主要目录

- `core/`：图片目录、候选检索、选图结果解析等纯逻辑。
- `services/`：图库、发送、回复完成通知、模型选图及诊断等有状态服务。
- `ui/`：宿主插件面板。
- `official/`：随插件提供的内置图片素材及说明。
- `tests/`：图库、选图、回复钩子、发送和诊断的回归测试。
- `plugin.toml`：插件元数据及模型用途声明。

模型用途声明目前是 `[plugin.models.eager_attachment]`，用途 ID 为 `eager_attachment`，能力为 `text`。该声明供宿主模型网关解析和绑定。它不是供应商模型名，也不是槽位 ID。

## 两种聊天路径

### 主模型工具路径

旧宿主不支持回复完成钩子时，插件注册 `sticker_list` 和 `sticker_send` 工具，并通过提示或提醒让聊天主模型决定是否调用。主模型可结合工具返回的图片说明选择图片。

这条路径不额外调用选图模型，但“是否调用工具”由聊天模型决定。积极度和每轮计数不能强制聊天模型调用，所以它不能严格兑现每 1 至 2 轮发一次。

### 回复完成钩子路径

支持钩子的宿主在一轮合格的普通文字回复完成后调用插件 `after_reply`。插件使用原回复上下文选择图片，并在回调结束前通过 `ctx.reply_tail.register(...)` 把图片登记到该回复末尾。

当前插件在此路径中通过：

```python
client = await self.plugin.ctx.models.get_client()
response = await client.chat.completions.create(
    model="eager_attachment",
    ...
)
```

调用宿主插件模型网关。它是一次独立的选图推理请求，不会续写聊天，也不读取正在运行中的聊天模型请求上下文。回复完成钩子只保证插件获得判断机会，不保证一定选中或显示图片。

当前 `services/reply_completed.py` 的主要约束：

- 选图请求超时为 12 秒；宿主回调上限为 15 秒。
- 每轮最多将 16 个候选交给选图模型。
- 选图输出上限为 4096 tokens；截断、无效输出、超时或 `no_match` 均跳过本轮。
- `eager_attachment_turns` 只在爱发档且非 `every_reply` 时控制连续未配图轮数，其它档的门槛为 1。
- `every_reply` 会改变候选复用、冷却和概率行为，但仍不会强行采用模型拒绝的图片，也不保证每轮实际送达。
- 发送总开关默认关闭，必须由用户明确开启。

## 宿主支持现状

### PR #3585：回复完成通知钩子

PR [#3585](https://github.com/Project-N-E-K-O/N.E.K.O/pull/3585) 已于 2026-11-03 合并。宿主提供插件订阅普通文字回复完成通知，以及把图片登记到原回复末尾的接口。

该 PR 解决的是“回复结束后由插件获得选图机会并提交图片”，**不负责替插件提供免绑定的模型调用**。

### PR #3741：插件模型跟随宿主档位

PR [#3741](https://github.com/Project-N-E-K-O/N.E.K.O/pull/3741) 已于 2026-11-22 合并。宿主增加 `host_follow` 模型槽位，并将新插件声明的模型用途自动绑定到共享的 **Familiar model / agent（使魔模型）**。绑定调用时解析宿主当前 `agent` 档位配置，宿主更改供应商、模型或凭据后，下次请求读取新的配置。模型凭据不会复制进插件自己的配置。

它面向本目标的意义是：插件可以继续使用现有 `ctx.models` 网关请求 `eager_attachment`，而不用要求用户为该用途另外创建和绑定插件模型槽位。

需要区分：

- `agent` 是宿主使魔/任务模型档位，不等于聊天正在使用的 `conversation` 模型，也不保证与聊天模型型号相同。
- 这个能力仍然发起独立模型请求，只是复用宿主管理的使魔模型配置。
- 自动绑定不等于模型必定可用。如果宿主 `agent` 档位解析不出可用 HTTP 对话接口，模型请求仍会失败。
- 插件服务器按宿主“使魔模型”能力进行自动绑定。不要仅凭 PR 已合并，就假定当前测试机器上的 `sticker_manager/eager_attachment` 已经实际绑定并成功调用。

## 自动绑定边界

宿主实现 `ModelConfigService.ensure_host_follow_binding(...)`，成功安装插件后读取其 manifest 模型用途，并将符合能力条件且尚未明确配置的用途绑定到共享 `agent` host-follow 槽位。

自动绑定是非覆盖式的：

- 已有有效插件模型绑定会保留，不会被改成使魔模型绑定。
- 用户曾明确解绑的用途会保留解绑状态，不会在插件更新时重新自动绑定。
- 新安装或触发宿主安装后自动绑定流程的更新，才是面向全新默认绑定的主要场景。
- 对于已安装且已有 `eager_attachment` 绑定的用户，保留其选择是宿主的预期行为；如果要验证默认免配置路径，应使用隔离测试用户/配置，或创建一个全新测试安装。不要为了测试直接删除用户现有配置。

因此，当前应把两个状态分开判断：

1. **功能集成状态**：插件是否仍声明并使用 `eager_attachment`；宿主是否实现 host-follow 和安装时自动绑定。
2. **当前运行实例状态**：该安装实例的 binding 当前指向什么、宿主 `agent` 是否可用、插件选图测试是否成功、回复完成 hook 是否订阅成功。

## 当前代码状态与已知缺口

- 本地插件源码 `plugin.toml` 版本为 `0.9.5`，已声明 `eager_attachment`。
- 回复完成 hook 的选图和原回复图片登记链路已经存在。
- 宿主 hook 已合并；宿主模型自动绑定功能也已合并。
- 当前本地插件文档 [README.md](../README.md) 和部分选图说明仍写着用户需要手动绑定“回复配图选图”，并描述未绑定时 hook 路径不回退。这些说明是基于旧宿主行为，应该在完成新宿主验证和插件兼容改动后更新，不能直接当成 #3741 合并后的最终用户指引。
- 插件对 `model_usage_not_bound` 有独立诊断状态；这一诊断适合找出“自动绑定没有发生”，不应再把手动绑定作为新安装用户的默认解决方案。
- 需要验证现有安装更新后的体验。`#3741` 保留既有绑定，因此“给用户无额外配置”应先用干净的测试安装证明，再决定现有安装是否提供明确的迁移/转换选项；不得静默覆盖用户已有模型选择。
- 现有 hook 托管模式会撤下 `sticker_list` / `sticker_send`，而模型调用失败时不会自动回到旧工具模式。这是独立于自动绑定的韧性问题。后续可以设计安全降级，但必须防止同一轮由 hook 和聊天工具重复发图。
- 自然/爱发档的选图尝试节奏可以达到每轮评估，但实际发图仍取决于模型耗时、候选相关性、纯文字/严肃内容判断、冷却及宿主投递。对用户表述应是“按轮次触发选图尝试”，而不是保证每轮必发。

## 建议接手顺序

1. 在隔离的宿主用户数据/测试 profile 中安装或更新该插件，确认安装后宿主创建 `sticker_manager` 的 `eager_attachment` → `host_follow(agent)` 绑定。
2. 不改用户的真实绑定和凭据；查看插件模型绑定 API/管理页的状态，确认其来源为跟随宿主档位，而不是独立手填槽位。
3. 确认宿主当前 `agent` 有可用 HTTP 对话模型，再在插件面板运行“测试选图”。此探针只验证模型选择，不实际发送图片。
4. 打开插件发送总开关，使用新对话确认 hook 状态为已订阅；观察选图状态、模型耗时和登记状态，然后进行受控实发。
5. 覆盖未绑定/agent 未配置、模型超时、输出截断、`no_match`、用户要求纯文字、登记失败和新输入打断等路径。
6. 根据验证结果更新用户文档：新安装无需绑定插件模型；宿主 agent 不可用时给出准确诊断；对旧绑定只提供显式选择，不擅自覆盖。

验证应分别确认“插件调用到了宿主模型”、“模型选出了图片”、“图片登记到原回复”和“前端实际显示”四个结果。它们是不同阶段，不能仅凭钩子订阅成功或模型请求成功就判断端到端已稳定。
